# v7.4.5 · 修多源加速的两个真实缺陷

## 一、修了什么

### 1. 换 `<base>` 后同源资源被拖去镜像（会挂起）
v7.4.4 把资源源切到镜像时，`<link>` 里的 `manifest.json` / `favicon.png` /
`icons/*.png` **也跟着换了源**。而 jsDelivr 的 `gh` 端点对
**`*.png` 与 `*.html` 一律 301 到 `raw.githubusercontent.com`** ——
该域名在国内不可达，请求会长时间挂起。

修法：在改 `<base>` **之前**把这些链接固化成绝对 URL
（`keep[i].href = keep[i].href`，此刻 base 仍是 `./`，解析结果就是本站地址），
之后它们不再受 base 影响。**不写死路径**，两种部署根都适用。

### 2. 入口页 iframe 没铺满（v7.4.4 的回归）
`<iframe>` 的 id 从 `app` 改成 `ogl-frame`，但 CSS 选择器还是 `#app` →
iframe 只剩浏览器默认的 300×150 小框。已改为 `#ogl-frame`。
（入口页是 `must-revalidate`，修复立即生效，无需等新版本。）

## 二、实测数据（本机网络，brotli 后）

| 源 | wasm 主包 1.42MB | skwasm 1.47MB | 小文件 TTFB |
|---|---|---|---|
| fastly.jsdelivr（预热后）| 1.90s | 2.74s | 0.43s（最稳）|
| 本站 Netlify | 3.14s | 2.04s | 0.65s |
| cdn.jsdelivr | 3.96s | 45s ❌ | 1.15s（抖动大）|
| proxy.344977.xyz | >45s（99KB/s）❌ | — | 0.56s |

**结论：fastly 在主包上有 1.6~2× 优势，但 skwasm 上打平，且冷启动 6~19s、
抖动明显。** 所以选择放在**运行时**做（探针取当下最快者），而不是写死。

## 三、运行时选源机制

1. 候选（实测排序）：`fastly.jsdelivr` → 本站同源 → `cdn.jsdelivr`
2. 并行探测 13KB 的 `flutter_bootstrap.js`，取最快者（上限 1s）
3. 命中后改 `<base href>`（同源图标/清单已固化）→ 仅 Flutter 资源走镜像
4. 结果缓存 `localStorage`（`ogl.cdn.v1`，6 小时）→ 之后零探测延迟
5. 全部失败 → 回退 `./`，与改动前行为一致

## 四、CI 增加预热
jsDelivr 对未请求过的文件要回源 GitHub（首次 6~19s）。CI 在提交 `app/`
后主动拉一遍关键文件（`main.dart.wasm` / `skwasm.wasm` / `main.dart.js` /
`canvaskit*.wasm`），把边缘缓存焐热；实际用户直接命中（1.6~2.3s）。

## 五、注意事项
- 桶内 `index.html` 被 `immutable` 缓存一年 → 优化必须走**新版本号**，
  不能原地改历史版本目录。
- `proxy.344977.xyz` 大文件吞吐 99KB/s，未纳入候选。
- main 分支零影响。
